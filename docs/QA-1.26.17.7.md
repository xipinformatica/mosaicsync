# MosaicSync 1.26.17.7 QA / permission-recovery stability checklist

1. Start from a normal AMO-installed Firefox profile with Frequently Visited enabled and Top Sites permission granted. Upgrade through Firefox's native extension update path only; do not use/remove a temporary same-ID `about:debugging` install for this test. Confirm the preference remains ON and suggestions remain visible when Firefox preserves the grant.
2. With Frequently Visited enabled, revoke/remove the optional Top Sites permission. Confirm the switch stays ON, suggestions clear, the localized permission-required status appears, and the direct **Grant permission** button becomes visible.
3. Click the recovery button. Confirm `permissions.request()` is initiated from the click gesture; on grant, the button disappears and suggestions return immediately without toggling OFF/ON. On denial, the switch remains ON and the recovery button remains available.
4. Grant/revoke Top Sites permission externally through browser permission UI while MosaicSync is open. Confirm `permissions.onAdded` / `permissions.onRemoved` refresh the section automatically.
5. Reload/update MosaicSync with Frequently Visited enabled and exercise the delayed startup reconciliation: if the browser exposes the permission shortly after startup, suggestions must self-heal; if permission remains absent, only the permission-required state/button remains.
6. Import a `.mosaicsync` profile whose Frequently Visited preference is enabled while Top Sites permission is absent. Confirm the imported preference remains ON and exposes recovery UI rather than being silently rewritten to OFF. Repeat through first-run Welcome profile import.
7. Switch through every supported UI locale (or run localization tests) and confirm the new permission button is present in all 32 catalogs with no English fallback/key text. Re-check long-language Settings layout.
8. Run the favicon stale-fan-out regression on both browsers: four identical URL/mode records share one resolver; while in flight one stays unchanged, one changes URL, one is deleted and one moves into an auto-icon-disabled Space. Only the unchanged record may hydrate, with one resolver call and one batch state write.
9. Re-run the 1.26.17.6 favicon quality/single-flight, failure/backoff, Frequently Visited memoization, first-paint hostile URL, prototype-pollution, Sync/concurrency, profile/security and parity regressions unchanged.
10. Run the complete suite, syntax checks and benchmark. Build Firefox/Chrome twice and require deterministic byte-identical runtime ZIPs. Extract the GitHub-ready source into a clean directory, rerun the full suite and rebuild packages byte-for-byte identical to the delivered ZIPs.
11. Diff both manifests against 1.26.17.6. Firefox may differ only in `version`; Chrome only in `version` and `version_name`. Re-check CSP, permissions, host permissions, secrets, absolute paths and runtime-package contents before submission.
